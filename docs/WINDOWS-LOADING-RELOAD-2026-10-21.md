# 응답 로딩 오류의 제한적 새로고침 복구

2026-10-21 KST. 부모 PR #74 `810d5aab1127d70c6dbed46f688d8c64a4052ca3`(OPEN).
브랜치 `feat/response-loading-reload-recovery`, 확장 0.4.41.

## 원인과 복구 효과의 구분

실제 `codex_disconnect_test`의 기존 탭에는 이전 안내문의 정상 답변과 사용자가 추가한 대화의 정상 답변이 표시됐다.
같은 계정·같은 대화 URL을 별도 읽기 탭으로 열면 두 assistant 턴에 `이 응답을 불러오지 못했습니다`가 재현됐다.
이 새 탭은 당시 Autopilot 미등록이며 관찰·전송·탭 제어를 수행하지 않았다. 콘솔 수집 오류는 없었다.
양쪽의 사용자/assistant 메시지 ID는 일치했다. 사용자의 새로고침 후 복구 보고도 이 현상과 양립한다.

따라서 이 문구는 생성 실패의 확정 증거가 아니다. Codex가 연 새 읽기 화면과 기존 화면 사이의
조회/렌더링 차이가 관측됐지만, Codex 조작·브라우저 상태·ChatGPT 조회 경로 중 근본 원인은 아직 미확정이다.
새로고침의 성공 여부는 원인 확정과 별도로 기록한다. 인증 자료·숨은 대화 상태를 추출하거나 접근 제한을 우회하지 않는다.

## 운영 연결 및 불변 조건

- 기존 축은 기본 off. 읽기 관찰이 승인된 정확한 등록 탭에 대해 localhost에서 1시간 복구를 명시적으로 허용한다.
  이 권한은 메시지·응답 재생성·비용·병합 권한을 추가하거나 기존 전송 승인 기간/횟수를 늘리지 않는다.
- 오류를 받는 즉시 영속 episode가 모든 후속 전송·이관을 차단한다. 먼저 30초 뒤 페이지 변경 없는 읽기 재관찰을 한다.
  읽기만으로 정상 표시가 돌아오면 새로고침 없이 두 신선한 안정 표본을 확인한다.
- 지속 오류에서는 마지막 사용자 메시지 ID의 지문, 정확한 오류 `role=status`, 완료된 마지막 턴,
  동일 등록 탭/그룹/URL/session epoch, 빈 편집기, 중지·모달·외부 경고 부재를 확인한다.
  초안 본문은 읽지 않는다. 인용·코드 속 오류 문구는 새로고침 증거가 아니다.
- SQLite Operation ID/의도를 먼저 기록하고 전역 슬롯을 확보한다. worker가 같은 탭의 DOM을 다시 검사하고
  서버의 실행 직전 허가를 받은 뒤 한 번 더 재검사한다. worker도 로컬 tombstone을 먼저 기록한다.
  실제 실행은 `chrome.tabs.reload(tabId,{bypassCache:false})` 한 번뿐이다.
- 미확인 전송·기존 복구·이관·진행 중 작업·승인/연결 변경이 있으면 실행하지 않는다.
  worker의 로컬 이관 상태도 확인한다. 큐/claim 재시작, 예외, 유실 ACK는 UNKNOWN이며 재시도하지 않는다.
- reload ACK는 성공 판정이 아니다. 이후 별도 challenge의 DOM에서 같은 사용자 요청에 속한 정상 assistant
  응답 ID/본문 지문·완료 상태를 확인하고 30초 이상 간격의 두 안정 표본으로 검증한다.
- 복구 후 기존 coordinator의 `observation_after`를 갱신한다. 이전 관찰로 즉시 계속 진행하지 않고,
  정상 결정기가 다시 읽고 안정성·승인·CI·이미 소비된 응답·claim 조건을 모두 통과해야 한다.
- 여러 축의 새로고침과 그 검증은 영속 전역 owner로 직렬화한다. 최소 시작 간격 60초,
  실패 후 2분부터 최대 15분 지수 백오프를 적용한다. 대기 중에도 신선한 읽기로 다시 확인한다.
  각 episode는 시간 제한이 있으며 정상 축의 coordinator/HTTP tick은 기다리지 않는다.
- 실패·불명은 해당 축만 Inbox 대기로 보낸다. 같은 사용자 요청에서 오류가 재발하면 추가 자동 복구를 하지 않고 검토를 요청한다.
  FAILED/UNKNOWN의 수동 해제는 별도 검토 대상이며, 이 구현이 불명 작업을 자동 소거하지 않는다.

핵심 파일: `local/loading-recovery.js`, `extension/loading-page.js`, `extension/loading-worker.js`,
관찰 transport/projector, runtime/coordinator, 서버 RPC, Inbox/운영 화면 및 이관·삭제 가드.
기존 DB는 백업 후 additive table만 생성하며 등록·기존 승인·전송 이력·Watchtower 귀속을 보존한다.

## 검증 경계

자동 테스트는 실제 runtime/SQLite/HTTP 구성, 직렬화 DOM, worker의 세션·초안·이관·허가·중복·재시작 가드를 검증한다.
격리 Playwright는 실제 unpacked MV3 확장과 폐기 가능한 localhost DB를 사용한다.
모의 페이지에서 지속 오류→읽기 재확인→동일 탭 reload 1회→정상 두 표본 검증 및
지속 실패→축별 Inbox→추가 reload/메시지 없음 경로가 통과했다. 실제 30초 간격을 기다리며 안정화 조건을 줄이지 않는다.
기존 격리 trace와 Windows/Ubuntu CI artifact에 두 시나리오가 포함된다. **실제 계정 trace가 아니다.**

실기기 시작 상태: 메시지를 추가하지 않고 오류가 재현된 읽기 탭 1개를 `codex_loading_test` 그룹에 격리했다.
기존 6개 작업축·6개 연결·6개 Autopilot 전송 기록을 백업/기준값으로 보존했다.
0.4.40 설치 소스가 부모 커밋과 일치함을 확인한 뒤 백업하고 0.4.41 소스 24개 파일을 실제 경로에 적용했다.
설치 소스 버전은 실행된 worker 또는 실제 복구 성공의 증거가 아니다.
실제 실행 결과·정확한 최종 CI는 PR의 후속 검증 기록과 ignored `.autopilot/acceptance-evidence/2026-10-21-loading-*`에 남긴다.
실제 실패를 지우거나 모의 페이지로 대체해 성공으로 보고하지 않는다.

## 실제 Windows Chrome 후속 실행

사용자의 v0.4.41 Reload 완료 후 실행된 worker의 `loading-reload-1` 지원과 신선한 읽기 수신을 확인했다.
기존 대화로 처음 등록한 탭의 epoch 재연결이 localhost에서 거부되는 연결 누락을 수정했다.
같은 물리적 탭·그룹·session·최근 확정 주소·새 epoch를 모두 확인하는 명시적 재연결만 허용하며,
다른 대화 이동/미확정 등록/epoch 누락은 거부하는 회귀 테스트를 추가했다.
실제 `codex_loading_test` 재연결은 Codex가 localhost에서 수행했다. 기존 등록 삭제/재페어링은 하지 않았다.

복구 허용 버튼의 브라우저 확인창 처리 도구가 시간 초과되어, 이미 승인된 동일 범위를 로컬 same-origin API로 적용했다.
대상 탭의 접근 정책을 우회하거나 직접 새로고침·전송·재생성하지 않았다. 이후 모든 단계는 실제 server/worker가 실행했다.
실제 Chrome 조작/화면 확인은 지원되는 브라우저 Playwright 인터페이스를 사용했다.

| KST | 실제 증거 |
| --- | --- |
| 11:23:55 | 오류의 신선한 수신으로 `REOBSERVE`; 모든 전송 차단, 변경 없는 읽기 재확인 예약 |
| 11:24:55 | 지속 오류·동일 요청·빈 입력창 재확인 → SQLite intent/claim/실행 직전 허가 → 동일 물리적 탭 `1042919794` reload 1회 → `POST_RELOAD` |
| 11:25:55 | 별도 challenge의 새 DOM: `verified:true`, 동일 사용자 요청 지문, 완료된 정상 응답 지문, 초안/생성/경고 없음 → `VERIFYING` |
| 11:26:55 | 두 번째 새 challenge에서 같은 정상 응답 지문 확인. 표본 요청 시각 차이 60,049ms → `DONE / LOADING_RELOAD_INDEPENDENTLY_VERIFIED`, Operation 완료 및 전역 슬롯 해제 |

**실제 단일 축의 오류 감지→전송 차단→읽기 재확인→같은 탭 자동 reload 1회→독립 정상/안정 검증은 통과했다.**
Operation `57d549ba-477e-45f2-a5c1-cbab254b1f95`의 이력은 유지했다. 이후 1분 이상 동일 완료 상태와 전송 6건 유지도 확인한다.
이 테스트 축은 관찰 모드이며, 사용자 지시대로 후속 메시지 승인이나 전송을 추가하지 않았다.
복구 완료 후 실제 `계속 진행`까지 검증했다는 의미는 아니다. 정상 자동화 게이트 재진입과 기존 승인/CI/중복 방지는 코드·격리 E2E로 검증했다.

새로고침 후 실제 화면에는 이전 assistant 응답 두 개가 다시 나타났다. 이는 복구 효과의 증거이며 근본 원인 확정은 아니다.
정상 원본 탭도 완료된 턴 2개·로딩 오류 0개로 유지됐다.
읽기 전용 SQLite 비교에서 기존 작업축 6개/연결 6개/모든 메시지 설정/전송 이력 6개가 모두 보존됐다.
새 축 1개만 추가했으며 메시지 전송 설정/자동 진행 schedule은 만들지 않았다. 추가 실제 메시지·재생성은 0회다.

실제 지속 실패/다중 축 동시 오류와 복구 후 실제 후속 메시지는 이 실행에서 검증하지 않았다.
