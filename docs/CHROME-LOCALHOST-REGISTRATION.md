# Chrome 미등록 탭 발견 → localhost 등록·연결 (PR #59 이후)

> 현재 구현 기능: 이미 인증 페어링된 MV3 확장이 **Chrome 그룹에 속한 미등록 ChatGPT 탭 후보**를 로컬 서버에 제한적으로 보고하고, 사용자가 localhost 화면에서 특정 작업축과 후보를 선택하면 확장이 실시간 상태를 재검증해 등록한 뒤 서버가 해당 Workstream과 연결합니다.
> **이 동작은 탭 등록이지 메시지 발송 승인이나 자동 개발 실행 승인이 아닙니다.** 기존 등록·이관 실패 기록은 보존됩니다.

## 사용 흐름

1. Chrome 확장 프로그램과 로컬 서버가 이미 페어링돼 있는지 확인합니다. 다시 페어링하면 기존 매핑을 지우는 경로가 있으므로 연결 상태가 online이면 **재페어링하지 않습니다**.
2. 등록하려는 ChatGPT 탭을 Chrome 그룹(예: `codex_test`)에 둡니다. 일반 홈(`https://chatgpt.com/`), 기존 채팅, ChatGPT 프로젝트 새 채팅 진입점 등 **허용된 ChatGPT 경로**만 후보가 됩니다.
3. `http://127.0.0.1:48173/` 관리 화면의 **Chrome 확장 프로그램 연결 → 미등록 ChatGPT 탭 찾기 · 바로 연결** 영역을 확인합니다. 후보는 확장의 다음 동기화에서 보입니다.
4. 대상 후보의 그룹·제목을 확인하고 연결할 **기존의 미연결 Workstream**을 선택한 다음 **이 탭 등록·연결**을 누릅니다. 이름이 그룹과 같은 작업축을 기본 선택하더라도 실제 버튼 클릭은 필요합니다.
5. 서버는 5분 만료의 1회용 등록 의도를 저장하고, 다음 인증된 확장 동기화에 전달합니다. 확장이 **동일 tab ID/window ID/group ID/URL SHA-256**인지 검증한 뒤 현재 Chrome에 등록하고 새 세션을 서버에 보고합니다.
6. 서버는 확장의 독립적인 새 등록 heartbeat를 확인한 후에만 Workstream 연결을 확정합니다. 성공하면 목록에 **등록·연결 완료 / 연결됨**이 표시됩니다. 자동 전송·후속 관찰은 **별도 승인**이 필요합니다.

## 안전성과 예외

- 후보에 **대화 URL 전체, 대화 본문, 입력 초안, 토큰**을 넣지 않습니다. 서버에는 탭·그룹 번호(브라우저 세션 범위), 제목·그룹 라벨, ChatGPT 경로 유형, URL의 SHA-256만 저장합니다. 미등록 후보 탐색은 이미 페어링된 사용자 브라우저에서만 실행됩니다.
- 예전 `missing` 탭 또는 다른 Workstream 연결을 새 후보로 자동 전환하지 않습니다. 이미 연결된 작업축의 일반 신규 등록 요청은 거부합니다. 아래의 새 채팅 주소 확인만 예외이며, 기존 등록 해제는 별도 명시적 조치입니다.
- 선택 후 탭이 다른 그룹/창으로 이동하거나, 다른 ChatGPT 대화로 이동하거나, 그룹이 바뀌면 등록하지 않고 이유를 표시합니다.
- 실행 도중 확장이 종료되거나 응답이 유실돼도 같은 등록 의도/세션 ID만 재확인해 중복 등록하지 않습니다. 기한이 지난 의도는 실행하지 않습니다.
- 등록된 ChatGPT 창에 임의 메시지를 넣거나 `계속 진행` 승인 범위를 넓히지 않습니다.
- 서버의 `register-chrome` 엔드포인트는 일반 로컬 컨트롤 API와 마찬가지로 `127.0.0.1` Host, same-origin `Origin`, JSON POST를 요구합니다. 확장 ACK는 페어링 인증 토큰이 필요합니다.

## 검증 범위

- `tests/chrome-enrollment.test.js`: 필터/개인정보, 다른 URL·그룹·창 거절, 동시/중복 요청·실패/만료, 재전달 멱등성, 등록 확인 없는 ACK 불인정, 기존 연결 보존.
- `e2e/extension-browser.mjs`: 독립 Playwright 프로필과 로컬 모의 ChatGPT 페이지에서 **확장 페어링 → 미등록 그룹 탭 발견 → localhost 등록·연결 → 인증된 확장 수락 → 서버 연결 확인**.
- 실제 사용자 Chrome/ChatGPT 프로필에서의 동작은 별도 Windows Acceptance가 필요합니다. 읽기 전용 화면과 합성 E2E 테스트를 실제 계정에서의 메시지 전송으로 오해하지 않습니다.

## 남은 실기기 확인

기존 `codex_test` 탭과 `codex_test` Workstream을 유지한 채 확장·서버를 최신 버전으로 갱신하고, localhost에서 후보를 한 번 선택해 연결합니다. **기존 `자동 이관 검증 1` missing 등록은 변경하지 않습니다.**

등록·연결이 확인돼도 후속 프롬프트 실제 1회 전송·첫 답변 완료·Watchtower·복구·이관·메신저는 별도 단계에서 검증해야 합니다.

## 새 채팅의 첫 메시지 뒤 주소 확인 (확장 0.4.34)

실제 Windows Chrome 테스트에서 첫 메시지 전송과 첫 답변은 성공했으나, `/`에서 `/c/...`로 주소가 바뀌면 등록이 `url-changed`가 되어 다음 전송이 차단되었다. 이 경우 기존 세션을 지우거나 다른 탭으로 옮기지 않고 localhost에서 **이 탭의 생성된 대화 주소 확인·연결**을 누를 수 있다.

- 이 경로는 localhost 등록 의도로 최초 등록한 새 채팅/프로젝트 시작 화면에만 제공한다. 기존 대화에서 다른 대화로 이동한 경우에는 제공하지 않는다.
- 같은 물리적 탭·창·그룹·브라우저 세션과 같은 프로젝트여야 한다. 이전/현재 URL 지문, 원본 등록 의도와 대상 작업축을 다시 검증한다. 다른 작업축이나 과거 missing 등록으로 바꿀 수 없다.
- 별도 5분 만료 의도를 승인한 뒤에만 확장이 기존 세션의 주소를 갱신한다. 같은 의도 재전달은 멱등적이며, 원본 세션 ID·그룹 ID·Workstream을 유지한다. 서버는 새 연결 heartbeat와 새 URL 지문 ACK를 확인한다.
- 대기 중인 메시지 명령이 있으면 주소 확인을 시작하지 않는다. 주소 확인 시작/완료 시 해당 작업축의 기존 관찰·자동 전송 승인을 중단한다. 완료 후 읽기 관찰과 남은 전송 범위를 새로 승인한다.
- 이 기능의 추가 회귀/E2E 결과와 실제 Chrome의 첫 메시지 전송 근거는 구분한다. 확장 업데이트 후 실제 주소 확인 및 두 번째 조건부 메시지 전송은 별도 확인 대상이다.

### 확장 Reload 경계 (0.4.36)

실제 Windows Chrome Reload가 `chrome.storage.session`의 브라우저 식별자를 초기화해 원래 `url-changed` 탭이 `needs-rebind`로 바뀌는 추가 차단을 확인했다. 첫 메시지 뒤 새 대화로 전환한 탭을 명시적으로 확인하는 경로에 한해 이를 지원한다.

후보와 5분 의도를 현재 브라우저 식별자의 SHA-256에도 바인딩한다. 확인 도중 다시 Reload하면 실행을 거부한다. 원래 등록 의도의 탭·창·그룹·이전 URL 지문과 같은 프로젝트라는 조건을 유지하며, 세션이 하나인 그룹만 명시적으로 복구한다. 다른 등록, 여러 세션이 있는 그룹, 기존 대화 사이의 이동은 자동 복원하지 않는다. 새 후보 탐색 자체로는 등록을 변경하지 않는다. 격리 E2E에서는 session 저장소 초기화 뒤 대상 1개만 복구하고 다른 20개 등록이 `needs-rebind`로 남음을 확인한다.
