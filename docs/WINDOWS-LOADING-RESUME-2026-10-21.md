# 응답 복구 후 재개와 동시 복구 검증

기준: PR #75 `b5df985351eb12d849eec1e9e627f6b45c0933db`, 확장 0.4.41.
브랜치: `feat/loading-recovery-resume-acceptance`. 실제 계정 검증과 격리 fixture 결과를 구분한다.

## 변경

다섯 축에서 실제 1분 worker heartbeat와 응답 검증을 직렬화하면 뒤쪽 축이 최초 10분 기한을 넘길 수 있었다.
`WAIT_SLOT` 대기는 생성 시각부터 최대 30분 또는 기존 복구 권한 만료 중 이른 시각으로 제한한다.
대기 재관찰마다 기한을 연장하지 않는다. 실행 슬롯을 얻으면 기존 5분 실행/검증 기한을 적용한다.
전역 owner/60초 최소 간격/실패 백오프/같은 요청 reload 최대 1회/메시지 승인은 변경하지 않는다.

3개와 5개 동시 오류의 FIFO 대기, 정상 축의 독립 전송, 각 축의 기존 승인 보존을 runtime/SQLite 구성으로 검증한다.
CI/비용/로컬 테스트/연결/길이/제공자 제한을 복구 완료 후 다시 관찰했을 때 후속 전송하지 않는 회귀 테스트를 포함한다.
Playwright/MV3 E2E는 오류 발생 전에 승인한 1회 campaign을 사용하고, 복구 완료 뒤 새 정상 관찰을 통과해
`계속 진행` 1회와 다음 응답 완료를 확인한다. 실제 안정화 시간을 줄이거나 실제 DB 시계를 변경하지 않는다.

## 실제 Windows Chrome 환경

처음 만든 테스트 탭 3개에는 전체 대화 로딩 오류가 나타났다. 본문의 공식 `다시 시도`를 각 1회 클릭한 뒤 정상 대화가 표시됐다.
이는 Autopilot의 개별 응답 새로고침 성공이 아니다. 사용자 사용량 영향이라는 가설은 있으나 근본 원인은 확정하지 않았다.

사용자가 이후 테스트 그룹과 탭을 닫았다. 14:49 KST에 서버가 중지된 것을 확인하고 같은 SQLite로 직접 다시 실행했다.
이전 등록 intent는 보존했다. 완료되지 않은 새 테스트 축 3개에 새 탭을 등록했으며 원래 7개 작업축/연결은 변경하지 않았다.
처음 복원한 두 탭이 정상, 한 탭이 응답 로딩 오류였다. 빈 편집기와 생성 없음 확인 후 정상 테스트 탭 2개만 각각 1회
오류 재현용 수동 reload를 했다. 이 동작은 자동 복구 횟수에 합산하거나 자동 복구 성공으로 보고하지 않는다.
이후 테스트 범위 내 읽기 탭 2개를 추가하여 총 5개를 사용했다. 추가 메시지나 응답 재생성으로 오류를 유도하지 않았다.

동일한 기존 수락 테스트 대화를 다섯 물리적 탭에서 읽는 시나리오이며, 독립된 실제 개발 대화 다섯 개를 대표하지 않는다.
각 축의 tab/group/session/binding과 operation은 독립이다. 전송 권한은 자동 복구와 독립 정상 검증을 마친 축 하나에만 부여할 수 있다.
원래 메시지 한도는 소진됐으며, 새 1회 승인도 탭이 닫힌 동안 1시간이 지나 만료됐다.
15시경 사용자가 미사용 1회를 지금부터 1시간으로 재승인했다. 새 안내문/재생성/다른 축 전송은 승인 범위에 없다.

## 실제 관찰 기록

- `codex_loading_parallel_1`: 실제 오류 → 읽기 재확인 → 자동 reload 1회 → 오류 지속.
  `FAILED / LOADING_RELOAD_DID_NOT_RECOVER`와 해당 축 Inbox 대기를 확인했다. 반복 reload/전송하지 않는다.
- 다른 오류 축은 `WAIT_SLOT / LOADING_GLOBAL_BACKOFF`로 대기하고 정상 두 축은 새 읽기 수신을 유지했다.
- `codex_loading_parallel_2`, `_4` 역시 실제 reload 1회 뒤 오류가 지속되어 같은 FAILED/Inbox 분기로 종료됐다.

| 축 | 실행 직전 허가/시도 KST | 독립 재관찰의 실패 확정 KST |
| --- | --- | --- |
| parallel_1 | 14:57:02 | 14:58:01 |
| parallel_2 | 15:01:02 | 15:02:01 |
| parallel_4 | 15:06:01 | 15:07:01 |

세 요청의 실제 reload 시작은 겹치지 않았다. 앞선 실패 후 2분/4분 백오프와 신선한 재관찰 및 worker 주기가 적용됐다.
세 번째 요청의 완료 후 owner가 해제되고 failures=3, 다음 예산 시각에 8분 백오프가 반영됐다.
5개 실제 물리적 탭 중 오류 3개/정상 2개를 관찰했지만, 등록/시작 시각이 달라 **활성 복구 3개를 같은 순간 시작한 테스트는 아니다.**
서로 다른 실제 개발 대화의 3~5개 동시 복구 및 정상 축의 실제 메시지 실행도 별도 미검증이다.

원래 7개 축·연결, 모든 기존 메시지 설정과 전송 6건을 읽기 전용 SQLite 기준값과 비교해 동일함을 확인했다.
새 테스트 축 5개만 추가했고 실패 이력 3개와 Inbox 3개를 보존했다. 오류 축은 각각 paused, 정상 두 축은 paused=false다.
추가 실제 메시지/재생성은 0회이며 재승인된 1회도 사용하지 않았다. 복구가 성공하지 않아 후속 전송을 허용하지 않았다.
**이번 실제 Chrome의 복구→계속 진행→다음 응답 완료는 미완료다.** PR #75의 이전 단일 축 성공을 이번 성공으로 재사용하지 않는다.
UI와 관찰 결과는 일치한다. 사용량/조회/렌더링 등 근본 원인은 미확정이며 반복 새로고침으로 제한이나 실패 기록을 우회하지 않는다.

로컬 `npm run check`는 583/583 통과했다. 최종 Windows/Ubuntu Actions와 격리 E2E 결과는 PR 체크에 기록한다.

로컬 증거는 ignored `.autopilot/acceptance-evidence/2026-10-21-resume-*`에 보존한다.
실제 계정 스크린샷·대화 본문·계정 trace를 CI artifact에 업로드하지 않는다.
격리 Playwright trace만 기존 CI artifact에 남긴다. 등록/실패 이력 삭제, 승인 한도 초기화, PR 병합은 하지 않는다.
